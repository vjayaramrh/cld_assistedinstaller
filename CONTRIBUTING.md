## 🚀 Quick Start

### 1. Find Something to Work On

Browse our [Issues](https://github.com/vjayaramrh/cld_assistedinstaller/issues) page and look for:

**For First-Time Contributors:**
- `good first issue` - Perfect for newcomers
- `documentation` - Writing and editing tasks
- `help wanted` - We need your help!

**By Type:**
- `documentation` - Write, edit, diagram
- `code` - Build features
- `testing` - Add tests
- `design` - Create visuals

**By Skill Level:**
- `beginner friendly` - Easy to start
- `intermediate` - Some experience needed
- `advanced` - Complex tasks

### 2. Claim an Issue

Found something you want to work on?
1. Comment: **"I'd like to work on this!"**
2. Maintainer will assign it to you
3. Ask any questions you have
4. Get started!

### 3. Set Up Your Environment

```bash
# Fork the repository on GitHub
# Clone your fork
git clone https://github.com/YOUR_USERNAME/cld_assistedinstaller.git
cd cld_assistedinstaller

# Add upstream remote
git remote add upstream https://github.com/vjayaramrh/cld_assistedinstaller.git

# Create a branch for your work
git checkout -b my-contribution

# Make your changes
# ... (edit files) ...

# Commit your changes
git add .
git commit -m "Brief description of changes"

# Push to your fork
git push origin my-contribution

# Create a Pull Request on GitHub
```

### 4. Submit Your Pull Request

- Fill out the PR template
- Reference the issue number (e.g., "Fixes #123")
- Describe what you changed and why
- Request a review
- Be responsive to feedback

### 5. Get Your PR Merged! 🎉

- Maintainers will review (usually within 48 hours)
- Address any feedback
- Once approved, your PR gets merged
- You get recognized as a contributor!

## ✅ Contribution Guidelines

### Code Style

**Python (Ansible modules):**
- Follow PEP 8
- Use meaningful variable names
- Add docstrings
- Include type hints where helpful

**TypeScript (MCP server):**
- Use TypeScript strict mode
- Follow existing code style
- Add JSDoc comments
- Use descriptive names

**Documentation:**
- Write in Markdown
- Use clear, simple language
- Include examples
- Break into short paragraphs
- Use headings for structure

### Commit Messages

Use clear, descriptive commit messages:

```
Good:
✅ Add events_info module documentation
✅ Fix typo in API overview guide
✅ Create mock data for cluster responses

Bad:
❌ Update files
❌ Fix stuff
❌ WIP
```

### Pull Request Guidelines

**Before submitting:**
- [ ] Create a branch (don't work on main)
- [ ] Test your changes
- [ ] Update documentation if needed
- [ ] Reference the issue number

**PR Title Format:**
- `Add [feature]` - For new features
- `Fix [issue]` - For bug fixes
- `Update [docs]` - For documentation
- `Improve [thing]` - For enhancements

**PR Description:**
- What did you change?
- Why did you change it?
- How did you test it?
- Screenshots (if applicable)

## 🤖 Using AI to Help You Contribute

**This project embraces AI-assisted development!** We encourage you to use AI tools like Claude to help with your contributions.

### What AI Can Help With

**Learning & Understanding:**
- "Explain what an Ansible module does"
- "How does the Assisted Installer API work?"
- "What's the difference between MCP tools and resources?"

**Writing Documentation:**
- "Help me explain this concept for beginners"
- "Review my documentation for clarity"
- "Suggest examples for this guide"

**Coding:**
- "How do I validate this parameter in Ansible?"
- "Review my module code for best practices"
- "Help me write test cases for this function"

**Debugging:**
- "Why is my API call failing?"
- "How do I fix this git error?"
- "Explain this error message"

### How to Use Claude Effectively

**Be specific:**
```
Good: "Explain how to structure an Ansible info module that retrieves cluster events"
Better: "I'm building an Ansible info module for the Assisted Installer events API.
Show me the basic structure with parameter validation and error handling."
```

**Share context:**
- Link to relevant documentation
- Show what you've tried
- Explain your goal
- Mention your skill level

**Iterate:**
- Ask follow-up questions
- Request clarifications
- Ask for alternatives
- Get explanations of suggestions

### Transparency

**In your PRs, feel free to mention:**
- "Used Claude to help structure this documentation"
- "AI-assisted code generation, human-reviewed and tested"
- "Claude helped me understand X concept"

**This is encouraged!** We want to normalize AI-assisted development while emphasizing human oversight.

## ❓ FAQ

### "Is this really beginner-friendly?"
**Yes!** We have tasks for all skill levels. Start small and grow.

### "What if I make a mistake?"
**That's okay!** Mistakes are learning opportunities. We'll help you fix them.

### "How long does review take?"
**Usually < 48 hours.** We prioritize quick, helpful feedback.

### "Can I work on multiple issues?"
**Yes, but please finish one before claiming another** to give others opportunities too.

### "What if someone is already working on what I want?"
**Comment on the issue!** Maybe you can collaborate or find a related task.

### "I don't know Python/TypeScript. Can I still help?"
**Absolutely!** Documentation, testing, design, and community contributions are just as valuable.

### "How much time do I need to commit?"
**Any amount!** Contributions range from 30 minutes to 20+ hours. Do what works for you.
